# ADR-002: アーキテクチャ強制 — ドキュメント記述ではなくカスタムリンター+構造テストで規則を機械的に適用する

**ステータス:** 承認済み  
**作成日:** 2026-06-05  
**決定者:** プロジェクトオーナー

---

## Context（背景）

現在、リポジトリのアーキテクチャ規則（「エージェント定義は `agents/` に置く」「フック実装は `hooks/` に置く」「フックは `settings.json` に登録する」等）は `CLAUDE.md` のドキュメント記述のみで示されている。

この方式には以下の限界がある。

1. **検出不可能**: 規則への違反が発生しても、自動では検知されない
2. **阻止不可能**: エージェントがルールを見落とした場合、コミットされてしまう
3. **修復手順の欠如**: 違反が発見されても、どう直すべきかがエラーメッセージに含まれない
4. **テスト不在**: 構造的な整合性（例: `settings.json` のフック参照先ファイルが実在するか）を検証する仕組みがない

ハーネスエンジニアリングの実践では、アーキテクチャ規則の遵守を「カスタムリンター」と「構造テスト」によって機械的に担保することが推奨されている。これにより、ドキュメントへの依存から抜け出し、違反を「発生時点で即座に」検出・阻止できる。

---

## Decision（決定）

アーキテクチャ規則の強制を **カスタムリンター (`hooks/arch-lint.js`) + 構造テスト (`hooks/structure-test.js`)** によって機械的に実施する。

### 実装する機構

#### hooks/arch-lint.js（アーキテクチャリンタ）

Claude Code の `PostToolUse` フック（Edit/Write 後）として実行する。以下の規則を検査する:

| 規則 ID | 検査内容 |
|---------|---------|
| ARCH-001 | `agents/` 以外に `.md` エージェント定義が配置されていない |
| ARCH-002 | `hooks/` 以外にフック実装 (`.js`) が配置されていない |
| ARCH-003 | `rules/` 配下のファイルが `{lang}/{category}.md` の命名規則に従っている |
| ARCH-004 | `settings.json` に記載されたフックコマンドが参照するファイルが実在する |
| ARCH-005 | `CLAUDE.md` が 100行以内に収まっている |

エラー出力には必ず **修復手順** を含める:

```
[arch-lint] ARCH-004 違反: settings.json が存在しないフックを参照しています
  参照先: hooks/my-hook.js
  修復手順: hooks/my-hook.js を作成するか、settings.json から該当エントリを削除してください
```

#### hooks/structure-test.js（構造テスト）

`PreToolUse` フック（コミット相当の操作前）として実行する。リポジトリ全体の構造的整合性を検証する:

- `docs/adr/` に ADR ファイルが存在する
- `agents/` の各エージェントが `agents/` ディレクトリのみに配置されている
- `settings.json` が有効な JSON である
- 全フックファイルが Node.js として構文エラーなく読み込める

---

## Consequences（結果）

### ポジティブ

- アーキテクチャ違反を発生時点（ファイル編集後）に即座に検出できる
- 修復手順付きエラーメッセージにより、エージェントが自律的に問題を解決できる
- `settings.json` と実ファイルの不整合を継続的に検証できる
- ドキュメントの陳腐化を気にせず、コードが「唯一の真実」になる
- CI に組み込むことで人間のレビューでも同じ規則が適用される

### ネガティブ

- `hooks/arch-lint.js` および `hooks/structure-test.js` の実装・メンテナンスコストが発生する
- リンタの誤検知がエージェントの作業をブロックするリスクがある（抑制機構が必要になる可能性）
- リポジトリのアーキテクチャ規則自体を変更する場合、リンタも同時に更新する必要がある
- Node.js 環境が必須となるため、実行環境の依存が増える

---

## Alternatives Considered（検討した代替案）

### 案 A: ドキュメント記述のみで規則を示す（現状維持）

`CLAUDE.md` や `ARCHITECTURE.md` に規則を記述し、エージェント・人間に遵守を委ねる案。自動検出・阻止ができないため却下。

### 案 B: GitHub Actions の CI でのみ検査する

プッシュ・PR 時の CI でアーキテクチャ規則を検査する案。ローカルでの即時フィードバックがなく、違反が後から判明するため開発体験が劣化する。ローカルフックと CI の両方に適用することで共存可能だが、ローカルフックなしの CI のみは却下。

### 案 C: ESLint / 汎用リンタのカスタムルールを使用する

ESLint のカスタムルールとしてアーキテクチャ規則を実装する案。`rules/` や `agents/` の `.md` ファイルを対象とする場合、ESLint の適用範囲外になるため、専用スクリプトの方が柔軟性が高い。将来的なスケールアップ時には検討余地あり。

### 案 D: Pre-commit フックのみで検査する（git フック）

`git commit` 時の pre-commit フックで構造テストを実行する案。Claude Code エージェントが git コマンドを経由せずにファイルを編集する場合に検出が漏れるため、Claude Code の PostToolUse フックとの組み合わせが必要。両方を使うことは推奨するが、git フックのみの採用は却下。
