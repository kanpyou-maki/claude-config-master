# ADR-006: 状態ファイルを引き継ぎメモに絞り、大きさを 6KB に制限する

**ステータス:** 承認済み  
**作成日:** 2026-10-07  
**決定者:** プロジェクトオーナー

---

## Context（背景）

`PROJECT_STATUS.md` は「セッションの最初に必ず読む」「タスクが終わるたびに更新する」ファイルで、大きさの上限がなかった。配布先（vid-cut）では、4 日間（2026-10-03〜10-06）で 95KB になった。全 225 コミットのうち 119 がこのファイルを更新している。

節ごとの内訳は次のとおり。

| 節 | 大きさ | 中身 |
|----|-------:|------|
| 現在のフェーズ・進行中・次にやること・ブロッカー | 1.4KB | いまの状態 |
| 概要 | 0.9KB | プロジェクトの説明 |
| 完了済み | 3.9KB | 履歴（git log と PR に同じ情報がある） |
| 決定事項 | 30.9KB | 仕様・設計の決定 48 件 |
| メモ | 57.3KB | 進め方の決まり、モジュールの現状、ハマりどころ、PR ごとのレビュー結果 |

「いまの状態」は全体の 1.5% で、93% は決定事項とメモだった。必ず読まれて上限のないファイルは、次のセッションに確実に伝えたいことを書く場所として最も手軽なので、状態ではないものが集まる。

困ることは 2 つある。

1. **コンテキストを圧迫する。** 毎セッションの最初に全文を読み、そのあとの呼び出しでも読んだ内容がコンテキストに残る
2. **同じ事実が複数の節に書かれ、食い違う。** vid-cut では「状態ファイルの 1 か所だけ直して残りを忘れる」指摘が 3 回再発し、self-reviewer のチェック項目を足して対処していた

一方で、このファイルにしかない情報もある。作業中のブランチと途中で止まっている作業、次にやることの順序、人間の判断を待っている事項は、git log や PR から組み立て直せない。

---

## Decision（決定）

状態ファイルを残し、役割を「次のセッションへの引き継ぎメモ」に絞る。大きさを機械的に制限する。

1. **載せるのは 4 節だけにする。** 現在のフェーズ／進行中（ブランチ・PR・途中で止まっている作業）／次にやること／人間待ち（ブロッカーと未決の判断）
2. **「完了済み」「決定事項」「メモ」の節を持たない。** テンプレートからも削る。書きたいものは次の場所へ置く

   | 書きたいもの | 行き先 |
   |--------------|--------|
   | 終わった作業 | 書かない（git log と PR が記録している） |
   | 設計・仕様の決定 | `docs/adr/`、または `docs/` の設計書・仕様書 |
   | 進め方の決まり | `CLAUDE.md` か `.claude/rules/` |
   | モジュールの現状・知見 | `docs/` の該当する文書 |
   | 繰り返すハマりどころ | `docs/friction-log.md` |
   | レビューの結果 | PR の説明 |
   | マイルストーンのタスク分解 | `docs/exec-plans/active/`（完了したら `completed/` へ） |

3. **追記せず、書き換える。** 終わった項目はチェックを付けずに消す
4. **ARCH-007: `PROJECT_STATUS.md` は 6KB（6,144 バイト）以内。** `arch-lint.js` が、このファイルの編集時と全体検査のときに検査する。行数ではなくバイト数で測る（行数の上限は、1 行を長くすれば通ってしまう）。機械的に検査するのは大きさだけで、4 節に絞れているかは self-reviewer が確認する（黄金原則 G-17）
5. **更新するのは、PR を作る前とセッションを閉じる前。** 「タスクが終わるたび」をやめる。PR の前の書き換えは review-loop の最初の手順（Stage 0 の前）に入れ、self-reviewer が内容を確認する

---

## Consequences（結果）

### ポジティブ

- セッションの最初に読む量が 6KB で頭打ちになる
- 同じ事実を複数の節に書く構造がなくなり、節どうしの食い違いが起きにくくなる
- 決定と知見が、種類に合った文書に置かれる。必要なときだけ読めばよい

### ネガティブ

- **既存の配布先は棚卸しが要る。** `install.sh update` のあと、上限を超えた状態ファイルは ARCH-007 違反になり、review-loop の arch-reviewer が BLOCK する。中身を行き先へ振り分ける作業を、配布先ごとに一度行う必要がある（vid-cut は 95KB）。`install.sh update` は違反を表示する
- **行き先の文書も大きい場合がある**（vid-cut の `docs/design.md` は 107KB）。移すだけでは置き場所が変わるだけなので、行き先の分割と索引は別に必要になる
- 決定を一覧できる表がなくなる。一覧は `docs/adr/` のファイル名と、設計書の「関連 ADR」が担う
- 書きたいことが上限で書けない場面が出る。それが行き先を考えるきっかけになるが、行き先の文書が整っていないと摩擦になる

---

## Alternatives Considered（検討した代替案）

### 案 A: 状態ファイルをなくす

git log・PR・`docs/exec-plans/` から現在地を組み立て直す案。毎セッションの組み立て直しは 6KB のファイルを読むより高くつき、途中で止まっている作業と人間待ちの事項は復元できない。却下。

### 案 B: 上限を設けず、古い内容を別ファイルへ退避する

状態ファイルが大きくなったら履歴用のファイルへ移す案。何を移すかの判断が毎回要り、退避先が新しい溜まり場になる。そもそも状態でないものを書かせないほうが単純。却下。

### 案 C: 現在地を `CLAUDE.md` に書く

`CLAUDE.md` は自動で読み込まれるので読む手順が省ける。しかしサブエージェントにも毎回読み込まれ、規約のファイルが作業のたびに書き換わる。却下。

### 案 D: 行数で制限する

`CLAUDE.md` の 100 行（ARCH-005）と同じ方式。vid-cut の状態ファイルは 1 行が最長 580 文字あり、行数では大きさを抑えられない。却下。

### 案 E: 運用の決まりだけ書き、機械的には検査しない

ADR-002 のとおり、文書だけの決まりは守られなくなる。状態ファイルは最も手軽な書き場所なので、上限がなければ同じことが起きる。却下。
