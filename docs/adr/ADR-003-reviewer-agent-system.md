# ADR-003: レビュアーエージェント体系 — 2ステージ6エージェントのゲートキーパー型レビューパイプラインの導入

**ステータス:** 承認済み  
**作成日:** 2026-06-05  
**決定者:** プロジェクトオーナー

---

## Context（背景）

現在のリポジトリには `code-reviewer` と `security-reviewer` の2つのレビュアーエージェントが存在するが、どちらも**アドバイザリ（助言）型**であり、明示的な合否判定を行わない。この設計には以下の問題がある。

1. **レビュー結果の無視が可能**: レビューコメントを受け取っても、実装者がそれを反映せずに PR を作成できてしまう
2. **単一レビュアーの限界**: 汎用レビュアーが構造・スタイル・セキュリティ・テスト・ドキュメントの全観点を網羅しようとすると、観点間のトレードオフで見落としが生じる
3. **レビューの再現性が低い**: どの観点を審査したかが不明確なため、同じ変更に対してレビューの深さがセッションごとに異なる
4. **並行審査の仕組みがない**: 複数の観点を逐次的にレビューするため、独立した観点でも順番待ちが発生する

ハーネスエンジニアリングの実践では、**Ralph Wiggum ループ**（全員の合格が出るまでループを抜けられない仕組み）を用いて、品質ゲートを機械的に強制することが推奨されている。

---

## Decision（決定）

PR 作成の前提条件として、**2ステージ・6エージェントのゲートキーパー型レビューパイプライン**を導入する。

### レビュアー構成

| エージェント | 審査観点 | 代表的な合否基準 |
|-------------|---------|----------------|
| `self-reviewer` | 実装者による批判的な自己評価 | 意図通りに動くか・見落としはないか |
| `arch-reviewer` | アーキテクチャ規則（ARCH-001〜005）・依存方向 | 構造違反ゼロ |
| `style-reviewer` | コーディングスタイル・命名・ファイルサイズ・debug コード禁止 | 黄金原則 G-06〜G-09 クリア |
| `security-reviewer` | OWASP Top 10・シークレット漏洩・認証/認可 | 重大脆弱性ゼロ |
| `test-reviewer` | カバレッジ≥80%・テスト独立性・エッジケース | 閾値クリア |
| `docs-reviewer` | 実装とドキュメントの整合性・ADR 最新性・クロスリンク | 矛盾・陳腐化なし |

### パイプライン構造

```
実装完了
  │
  ▼
[Stage 0] self-reviewer
  │ 不合格 ──→ 修正 ──→ Stage 0 に戻る
  │ 合格
  ▼
[Stage 1] arch-reviewer + style-reviewer + test-reviewer（並行実行）
  │ いずれか不合格 ──→ フィードバックを受けて修正 ──→ Stage 1 に戻る
  │ 全合格
  ▼
[Stage 2] security-reviewer + docs-reviewer（並行実行）
  │ いずれか不合格 ──→ フィードバックを受けて修正 ──→ Stage 2 に戻る
  │ 全合格
  ▼
PR 作成 → マージ
```

### オーケストレーション

`skills/review-loop/SKILL.md` にパイプラインの制御手順を定義し、実装完了後に `/review-loop` スキルを呼び出すことで上記フローを自動実行する。

---

## Consequences（結果）

### ポジティブ

- **品質ゲートの機械的強制**: すべてのレビュアーが合格するまで PR を作成できないため、品質基準の形骸化を防ぐ
- **専門特化による見落とし削減**: 各レビュアーが単一観点に集中するため、汎用レビュアーでは見落とされがちな細部まで審査できる
- **並行審査による効率化**: Stage 1・Stage 2 の内部は並行実行するため、独立した観点のレビュー待ち時間を短縮できる
- **再現性の向上**: 審査観点と合否基準が明文化されるため、セッションをまたいでも同じ水準のレビューが再現される

### ネガティブ

- **実装コストの増加**: 6つのエージェント定義ファイルと `skills/review-loop/SKILL.md` を新規作成・維持する必要がある
- **フロー全体の所要時間増加**: 全ステージを通過するまでに複数回の審査サイクルが発生し、シンプルな変更でもオーバーヘッドが生じる可能性がある
- **不合格判定の品質依存**: レビュアーの判定精度が低い場合、誤った不合格により実装者の作業がブロックされるリスクがある
- **Stage 0 の客観性限界**: `self-reviewer` は実装者自身による評価であるため、根本的な設計誤りの見落としを完全には防げない

---

## Alternatives Considered（検討した代替案）

### 案 A: 単一の汎用レビュアーのみ（現状強化）

既存の `code-reviewer` に全観点の審査機能を追加し、合否判定も行わせる案。

**却下理由**: 単一エージェントが構造・スタイル・セキュリティ・テスト・ドキュメントを網羅すると、各観点の審査深度が浅くなる。また、観点間の優先順位判断が曖昧になりやすく、見落としが生じる構造的な問題が残る。

### 案 B: 人間レビューのみに委ねる

自動エージェントレビューを廃止し、PR の品質担保を人間のコードレビューに一任する案。

**却下理由**: このリポジトリはエージェント主体の開発環境を前提としており、人間が常時レビューできる保証がない。また、ARCH-001〜005 のような機械的に検査可能な規則まで人間が目視確認するのは非効率である。

### 案 C: 単一ステージで全レビュアーを逐次実行

ステージ分離なしに6つのレビュアーを順番に実行する案。

**却下理由**: 独立した観点（例: アーキテクチャとスタイル）を逐次実行する必要がなく、並行化のメリットを活かせない。また、後半のレビュアー（セキュリティ・ドキュメント）で不合格が出た際に、実装の根幹が変わりうる変更が発生し、前半のレビュー結果が無効になるリスクがある。ステージ分離により、安定した実装に対して最終審査を行う設計の方が合理的である。

### 案 D: CI/CD パイプラインに組み込む（自動化のみ）

エージェントレビューではなく、GitHub Actions 等の CI でリンター・テスト・セキュリティスキャンを自動実行し、合否を判定する案。

**却下理由**: CI ツールはコード解析が得意だが、設計意図の評価・ドキュメント整合性の意味的な判断・コンテキストを踏まえたアーキテクチャ評価は苦手である。エージェントレビューと CI は相補的であり、両方を組み合わせることが望ましいが、CI のみへの置き換えは質的な審査を失うため却下。
