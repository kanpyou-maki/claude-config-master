# ADR-005: フックの入出力規約 — 検出結果は終了コード 2 でモデルに渡し、起動は `$CLAUDE_PROJECT_DIR` 起点にする

**ステータス:** 提案中  
**作成日:** 2026-10-06  
**決定者:** プロジェクトオーナー

---

## Context（背景）

ADR-002 で「アーキテクチャ規則はフックで機械的に強制する」と決めた。この ADR は ADR-002 を置き換えず、フックの入出力の約束を補い、ARCH-004 の検査内容を広げる。

配布先（vid-cut、2026-10-02〜10-05 の 15 セッション）の履歴を集計したところ、フックは動いていても強制として働いていなかった。

| # | 事実 | 原因 |
|---|------|------|
| H-1 | 違反を検出してもモデルに届かない。ARCH-006 違反を出力しながら、モデルに渡った内容が空の記録がある | `arch-lint.js` と `post-edit-typecheck.js` が stderr に書いて終了コード 0 で終わっていた。PostToolUse の stderr がモデルに渡るのは終了コード 2 のときだけ |
| H-2 | フック実行 2,011 回のうち 1,029 回が `Cannot find module` で失敗 | `settings.json` の起動コマンドが相対パス（`node .claude/hooks/x.js`）。作業ディレクトリが `backend/` 等のとき解決できない |
| H-3 | 全フックが受け取った入力を stdout に書き戻していた（Write のときはファイル全文） | 「パススルー」のつもりの実装。PreToolUse / PostToolUse では、終了コード 0 の stdout は（規定の JSON でない限り）モデルに渡らない |
| H-4 | `pre-bash-git-push-reminder.js` が Bash のたびに起動し（1,508 回）、メッセージはモデルに届かない | matcher が `Bash` 全体。出力は stderr + 終了コード 0 |

フックの入出力の約束がどこにも書かれておらず、テストもフックを関数として呼ぶだけで、プロセスとしての終了コードと出力を検証していなかった。

---

## Decision（決定）

フックの入出力を次の規約に揃え、テストと ARCH-004 で機械的に守る。

1. **検出結果をモデルに伝えるフックは、stderr に書いて終了コード 2 で終わる。** 何もなければ何も出力せず終了コード 0 で終わる（`arch-lint.js`・`post-edit-typecheck.js`）
2. **ブロックせずに注意だけ渡すフックは、`hookSpecificOutput.additionalContext` の JSON を stdout に書く**（`pre-bash-git-push-reminder.js`）
3. **受け取った入力を stdout に書き戻さない**
4. **`settings.json` の起動コマンドは `node "$CLAUDE_PROJECT_DIR"/.claude/hooks/<name>.js` と書く。** フックの中でプロジェクトのルートが要るときも、作業ディレクトリより `CLAUDE_PROJECT_DIR` を優先する。相対パスのコマンドは ARCH-004 違反とする
5. **特定のコマンドだけに関係するフックは `if` フィールドで絞る**（例: `"if": "Bash(git push*)"`）
6. **`arch-lint.js` は、編集したファイルに関係する規則だけを報告する。** ARCH-004 は `settings.json` と `.claude/hooks/` の編集時、ARCH-005 は `CLAUDE.md` の編集時だけ検査する。ファイルを指定しない実行（`harness.json` の `commands.archLint`）では従来どおり全体を検査する
7. **モデルに渡すメッセージは 1 件 3 行に収める。** 違反メッセージにはファイルパスやリンク先など入力由来の文字列が入るので、`formatViolation` で制御文字（改行を含む）を空白に置き換え、各項目を 300 文字で切る

検証は `test/hook-contract.test.js`（フックをプロセスとして起動し、終了コード・stdout・stderr を確認する）が担う。

---

## Consequences（結果）

### ポジティブ

- 違反と型エラーが、発生した編集の直後にモデルに届く。ADR-002 の「発生時点で検出」が実際に働く
- 作業ディレクトリがどこでもフックが起動する
- `commands.archLint` が違反時に 0 以外で終わるので、スクリプトや CI から合否を判定できる
- git push 以外の Bash でプロセスを起動しなくなる

### ネガティブ

- 違反がモデルに届くようになるので、これまで見過ごされていた既存の違反（リンク切れなど）が、そのファイルを編集したときに報告される
- 配布済みプロジェクトの `settings.json` は `install.sh update` の対象外なので、起動コマンドは手で書き換える必要がある。書き換えるまでは、`install.sh update` と全体検査（`commands.archLint`）が ARCH-004 違反として書き換え後の形を示す
- `if` フィールドと `additionalContext` は Claude Code の新しめの機能。古いバージョンでは `if` が無視され、従来どおり Bash のたびに起動する（フック自身も git push かどうかを判定するので、誤った注意は出ない）

---

## Alternatives Considered（検討した代替案）

### 案 A: 終了コード 0 のまま、JSON の `additionalContext` で違反を渡す

ブロック扱いにならず穏当だが、違反は「直すべきもの」であり、終了コード 2 のほうが意図に合う。JSON を組み立てる分だけ実装も増える。注意だけを渡す git push のフックにはこの方式を使う。

### 案 B: フックの中でスクリプト自身の位置（`__dirname`）からルートを求める

起動に成功すれば有効だが、H-2 は起動そのものの失敗なので解決にならない。

### 案 C: 編集のたびに全体の規則（ARCH-004・005）も報告し続ける

違反が残っている間、無関係な編集のたびに同じメッセージがコンテキストに積まれる。全体の検査は review-loop の `commands.archLint` が担うので、編集時は編集したファイルに絞る。
