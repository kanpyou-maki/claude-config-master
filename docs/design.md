## 1. 概要

本ドキュメントは、claude-config-master リポジトリにハーネスエンジニアリングの概念を導入するための技術設計を記述する。「エージェントがリポジトリ自体から推論できる」構造を実現するため、5フェーズで既存リポジトリを段階的に変革する。

### 設計方針

1. **地図としての CLAUDE.md**: エージェントのエントリポイントは ~100行に保ち、詳細は `docs/` へ委譲する
2. **機械的アーキテクチャ強制**: ドキュメント記述ではなくリンターと構造テストで規則を担保する
3. **一級成果物としての計画**: 実行プランをリポジトリ内ファイルとして管理し、セッション横断で追跡する
4. **自律フィードバックループ**: GC エージェントが逸脱を検知し修正 PR を自動作成する

## 3. コンポーネント設計

### 3.1 CLAUDE.md（地図）

**責務**: エージェントのエントリポイント。詳細情報の所在を示す目次として機能する。

**制約**: 100行以内。以下のセクションのみ含む:
- リポジトリの目的（3行以内）
- 重要ファイルへのリンク集
- クイックスタート手順
- エージェント一覧（名前・役割・トリガーのみ）
- 開発フローの概要（フェーズ名と参照先のみ）

### 3.2 ARCHITECTURE.md

**責務**: リポジトリのドメイン・パッケージ階層をエージェントが即座に把握できるよう図示する。

**含む情報**:
- ディレクトリ責務の一覧表
- 依存関係の方向ルール（許可・禁止）
- 主要コンポーネント間のインタラクション図

### 3.3 hooks/arch-lint.js（アーキテクチャリンタ）

**責務**: ファイル編集後にアーキテクチャ規則への違反を検出する。

**検出項目**:
- `agents/` 以外への agent 定義の混入
- `hooks/` 以外へのフック実装の配置
- `rules/` の命名規則違反（`{lang}/{category}.md` 形式）
- `settings.json` のフック参照が実ファイルと不整合

**エラー出力形式**:
```
[arch-lint] 違反検出: hooks/ 外にフック実装が存在します
  ファイル: src/my-hook.js
  修復手順: hooks/ ディレクトリへ移動し、settings.json の参照を更新してください
```

### 3.4 docs/exec-plans/

**責務**: 実行プランを一級成果物としてリポジトリ内に管理する。

**ファイル命名規則**: `PLAN-{YYYYMMDD}-{slug}.md`

**プランファイル構造**:
```markdown
# PLAN-{date}-{slug}

**ステータス:** active | completed | abandoned
**作成日:** YYYY-MM-DD
**完了日:** YYYY-MM-DD（完了時のみ）

## 目標
## タスク一覧
- [ ] タスク1
- [x] タスク2（完了済み）
## 完了条件
## 備考
```

### 3.5 docs/golden-rules.md（黄金原則）

**責務**: リポジトリが常に満たすべき不変の原則を定義する。GC エージェントはこのファイルを参照して逸脱を検知する。

**原則例**:
- CLAUDE.md は常に 100行以内
- すべてのフックは `settings.json` に登録されている
- `docs/adr/` に記録のないアーキテクチャ変更はコミット不可
- テストカバレッジが 80% を下回ることを許容しない

### 3.6 agents/gc-agent.md（GC エージェント）

**責務**: 黄金原則への逸脱を定期的に検知し、リファクタリング PR を自動作成する。

**実行トリガー**: 週次（settings.json の cron フックで設定）

**処理フロー**:
1. `docs/golden-rules.md` を読み込む
2. リポジトリ全体をスキャンして逸脱を検出
3. 逸脱がある場合、修正差分を作成
4. PR を作成して逸脱内容と修正内容を報告

### 3.7 docs/QUALITY_SCORE.md

**責務**: 製品領域・アーキテクチャ層ごとの品質スコアとギャップを追跡する。

**更新タイミング**: GC エージェント実行時、フェーズ完了時

**スコア項目**:
- ドキュメント整合性（ADR・設計ドキュメントの最新性）
- テストカバレッジ
- アーキテクチャ規則遵守率
- 黄金原則達成率

### 4.1 settings.json フックスキーマ

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "node hooks/arch-lint.js"
          }
        ]
      }
    ],
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "node hooks/quality-gate.js"
          }
        ]
      }
    ]
  }
}
```

### 4.2 実行プランのライフサイクル

```
作成 (active/) → 進行中 (active/) → 完了 (completed/ へ移動)
                                   → 中断 (abandoned ステータスで active/ に残留)
```

## 5. トレードオフ

### 5.1 CLAUDE.md の簡素化

| 観点 | メリット | デメリット |
|------|---------|-----------|
| エージェント体験 | コンテキスト消費削減、指示の見落とし減少 | 詳細情報へのナビゲーションが必要になる |
| メンテナンス性 | 各ファイルが単一責任を持つ | ファイル数増加による管理コスト |
| 移行コスト | - | 既存の `CLAUDE.md` の内容を整理・分散する作業が発生 |

**採用判断**: コンテキスト効率の向上とエージェント自律性の改善を優先する（ADR-001 参照）

### 5.2 機械的アーキテクチャ強制

| 観点 | メリット | デメリット |
|------|---------|-----------|
| 信頼性 | 規則の見落としゼロ | リンタ実装・メンテナンスコストが発生 |
| 開発体験 | 修復手順付きエラーで即座に解決できる | 誤検知がブロッカーになりうる |
| 自動化 | CI/フックに組み込み可能 | - |

**採用判断**: ドキュメントによる手動管理の限界を超えるため、機械的強制を選択する（ADR-002 参照）

## 7. レビュアー体系（Ralph Wiggum ループ）

### 7.1 設計方針

従来の `code-reviewer` と `security-reviewer` はアドバイザリ（助言）型であり、明示的な合否判定を行わない。このため、レビュー結果を無視したまま PR 作成が可能な状態にあった。また、単一の汎用レビュアーが構造・スタイル・セキュリティ・ドキュメントの全観点を網羅しようとすると見落としが生じる。

この問題を解決するため、**専門特化したゲートキーパー型レビュアーエージェント**を複数配置し、すべてのエージェントの合格を PR 作成の前提条件とする仕組みを導入する。

いずれかのレビュアーが不合格を出した場合、実装者はフィードバックに基づいて修正を行い、当該ステージから再審査を受ける。このサイクルを「**Ralph Wiggum ループ**」と呼ぶ。全レビュアーが合格するまでループを抜けられないことで、品質の担保を機械的に強制する。

### 7.2 レビュアー一覧

| エージェント | 審査観点 | 代表的な合否基準 |
|-------------|---------|----------------|
| `self-reviewer` | 実装者による批判的な自己評価 | 意図通りに動くか・見落としはないか |
| `arch-reviewer` | アーキテクチャ規則（ARCH-001〜005）・依存方向 | 構造違反ゼロ |
| `style-reviewer` | コーディングスタイル・命名・ファイルサイズ・debug コード禁止 | 黄金原則 G-06〜G-09 クリア |
| `security-reviewer` | OWASP Top 10・シークレット漏洩・認証/認可 | 重大脆弱性ゼロ |
| `test-reviewer` | カバレッジ≥80%・テスト独立性・エッジケース | 閾値クリア |
| `docs-reviewer` | 実装とドキュメントの整合性・ADR 最新性・クロスリンク | 矛盾・陳腐化なし |

### 7.3 レビューパイプライン

全体は 2ステージ構成とし、軽量な自己評価（Stage 0）で明らかな問題を早期排除した後、並行審査で効率的に品質を担保する。

```
実装完了
  │
  ▼
[Stage 0] self-reviewer
  │ 不合格 ──→ 修正 ──→ Stage 0 に戻る
  │ 合格
  ▼
[Stage 1] arch-reviewer + style-reviewer + test-reviewer（並行実行）
  │ いずれか不合格 ──→ フィードバックを受けて修正 ──→ Stage 1 に戻る
  │ 全合格
  ▼
[Stage 2] security-reviewer + docs-reviewer（並行実行）
  │ いずれか不合格 ──→ フィードバックを受けて修正 ──→ Stage 2 に戻る
  │ 全合格
  ▼
PR 作成 → マージ
```

**ステージ分離の理由:**

- **Stage 0（自己評価）**: 実装の基本的な正しさを確認し、上位レビュアーへの無駄な依頼を防ぐ
- **Stage 1（構造・品質）**: アーキテクチャ・スタイル・テストは実装と密接に関連するため、実装の骨格が固まった段階で並行審査する
- **Stage 2（セキュリティ・ドキュメント）**: 実装が安定してからセキュリティと文書整合性を審査することで、手戻りコストを最小化する

### 7.4 スキル

`skills/review-loop/SKILL.md` に **Ralph Wiggum ループ**のオーケストレーション手順を定義する。

このスキルは以下を担う:

- 各ステージの起動順序と並行実行の制御
- レビュアーの合否判定結果の収集・集約
- 不合格時のフィードバック提示と再実行トリガー
- 全ステージ通過後の PR 作成フローへの接続

スキルの利用シーン: 実装完了後に `/review-loop` を呼び出すことで、上記パイプラインを自動でオーケストレートする。
